
# Feature Candidates

- [Study] Investigate HAMT (Hash Array Mapped Trie), CHAMP, and [Vavr](https://www.vavr.io/) persistent collections as drop-in alternatives to `HashMap`/`LinkedHashMap` where resizing is the dominant cost — primary candidates are the coordinate maps built per query row and the measure-value accumulators in `TabularRecordStreamReducer`; evaluate structural sharing benefits for immutable snapshots and GC pressure reduction.
- [Study] Evaluate [`ScopedValue`](https://openjdk.org/jeps/446) (JDK 21+ preview, stable in 25) as the thread-scoped backing for `LastLookupCache` / `LastLookupCache1`. Today the fast path does a `ThreadLocal.get()` which is a hash lookup in `Thread.threadLocals`; `ScopedValue` is designed to be cheaper (constant-time per-carrier read, no inheritance overhead, friendlier to virtual threads). Benchmark against the existing three strategies in `jmh/.../BenchmarkLastLookupCache` (plain CHM, `LastLookupCache1` ThreadLocal, `LastLookupCache1Volatile` shared-volatile) to quantify the win; also consider that `ScopedValue` is read-only once bound, so the caching update path would need a different publication mechanism (e.g. a small mutable holder bound once per query scope).
- [Study] Investigate how `UndictionarizedColumn` could propagate a *partial sort* to the output column. When the upstream table (DB `ResultSet`, DuckDB Arrow batch, etc.) already returns rows in a deterministic order on the groupBy key, `AggregatingColumnsDistinct` — which backs distinctness with a linked structure (`LinkedHash*`) — should be able to preserve that order end-to-end and expose the resulting column as sorted, avoiding a redundant post-aggregation sort. Scope: detect when the table advertises a sort, thread that metadata through `TabularRecordStreamReducer`/`AggregatingColumnsDistinct` without regressing unsorted sources, and mark `UndictionarizedColumn` as sorted so downstream reducers can skip re-sorting.
- [Study] Evaluate Stream Gatherers (JDK 24, `stream.gather(Gatherer)`) for stateful intermediate operations — primary candidate is `IConsumingStream.distinct()` which currently abuses `filter()` with a side-effectful predicate; secondary candidates are sliding-window aggregations and streaming deduplication if those use cases arise.
- [Study] Investigate how `IConsumingStream` could communicate phase transitions (sorted-leg → complement) and stream-level guarantees (distinctness) to downstream consumers. Today `UnderlyingQueryStepHelpersNavigableElseHash.distinctSlices` concatenates the sorted-leg stream with the complement streams, but the receiving consumer has no way to know when the switch happens — so it must check every complement slice against a `Set` of already-seen sorted slices. If the stream could signal "from this point on, elements are from the complement and are guaranteed not to duplicate any previous element", the consumer could skip the set lookup entirely. Similarly, if the stream could declare itself as *distinct* (no duplicates across its entire lifetime), consumers like `MultitypeNavigableElseHashColumn.append` would not need their own dedup checks. Possible designs: (a) a typed `IConsumingStream<PhaseTagged<T>>` wrapper that tags each element with its phase, (b) a callback/listener that fires on phase boundaries (e.g. `stream.onPhaseChange(phase -> ...)`), (c) metadata on the stream object itself (`stream.isDistinct()`, `stream.isSorted()`). Evaluate the trade-off between API surface, allocation overhead (tagging each element), and the performance win from skipping redundant lookups in the join and column-insertion hot paths. See [research.md § Joining Cuboids](docs/research.md#joining-cuboids) for the algorithmic context.

- [Drillthrough] Enable a measure to emit additional data alongside the source rows in DT output. The current `StandardQueryOptions.DRILLTHROUGH` path emits one entry per source row with the merged groupBy as `coordinates` and the per-aggregator (aliased) values as `values` — measures cannot contribute extra context. Typical use case is **FX**: a measure that converts a `notional` amount via an FX rate should emit the FX rate it picked next to the underlying row, so the DT consumer can audit `notional × rate = converted` per row. Possible designs: (a) extend `IMeasureQueryStep` with a `Map<String,?> drillthroughExtras(ISliceWithStep)` callback that the engine merges into the `values` map of every DT entry produced for that slice, (b) introduce a sibling `IDrillthroughEnricher` interface that a measure may opt into, keeping the core `IMeasureQueryStep` API untouched, (c) plumb extras through a new `IAggregationCarrier` subtype so the existing carrier pipeline handles them. Trade-off: option (a) is the most discoverable but bloats every measure's API; option (b) is the cleanest opt-in but adds a second extension point to remember; option (c) reuses an existing seam but constrains extras to per-slice scalar values. Beyond FX, the same mechanism could surface partition keys, decomposition shares, or custom-marker-derived audit data.
- [Drillthrough] Introduce **SemiDrillthrough** (`StandardQueryOptions.SEMI_DRILLTHROUGH` or similar): like DRILLTHROUGH it returns raw values from the DB without applying measure-side transformations, but **unlike DRILLTHROUGH it keeps the query's `groupBy`**. The output is one entry per resulting groupBy slice, with the table-side aggregator values exposed as-is. Useful when DT on very large datasets is unviable (too many rows to send back) yet the user still wants to *explain* a measure result without going row-per-row. Canonical FX use case: instead of one entry per booking row (DT), get one aggregate per CCY — quickly answers "is this number dominated by EUR or USD?" without materialising every booking. Implementation should mostly reuse the DT plumbing (skip measure-DAG transformations, emit the merged covering query result as `ITabularView`) but stop short of `executeDrillthrough`'s row-fan-out: keep the groupBy aggregation that the table layer already performs, and expose the per-aggregator outputs alongside the groupBy coordinates. Open questions: how to surface the user-side groupBy `coordinates` vs. the table-side `values` cleanly (a `ListMapEntryBasedTabularViewSemiDrillthrough` mirroring the DT view?); whether per-aggregator filters should still apply (yes, presumably); and how to interact with the [Drillthrough extras] feature above (FX rate per CCY would surface naturally if measures can contribute extras).
- [Pivotable] Fetch all column details in a single query
- [Pivotable] Query history. Persist (user-scoped) the queries a Pivotable user has submitted so they can re-open a previous query model, see when it was last viewed, and jump back into a prior cube/groupBy/filter configuration. The existing `QueryPlanRegistry.hasPlan(AdhocQueryId)` check is cheap and can decorate each history entry with a "view plan" affordance — UUIDs returned by `/cubes/query/asynchronous` are stable enough to use as the join key between history and the plan registry, since the engine now adopts them as its own `AdhocQueryId.queryId` (via `SubmittedQueryIdScope`). Open questions: storage shape (per-user in-memory ring buffer? `pivotable-app/persistence` for durability?), retention policy, and whether to share entries across browser tabs.
- [Pivotable] User-authored **calculated columns**, in-SPA. Today the only way to add a derived column is to register an `ICalculatedColumn` on the server-side `ColumnsManager` — a developer task that requires a redeploy. This feature exposes calc-column authoring as a Pivotable user action so an analyst can introduce e.g. `IsHomeWin = (HomeTeamGoals > AwayTeamGoals)` from the query view itself. Motivating case: a boolean column comparing two existing columns. Design sketch:
   - **Backing implementation**: first iteration uses {@link eu.solven.adhoc.model.column.EvaluatedExpressionColumn} (EvalEx-based) so the user can input any expression. The expression is evaluated row-by-row with the row's other column values as variables.
   - **Authoring UX**: dialog opened from the column wizard ("New calculated column"). Fields: name, expression. **Preview pane** uses the current query result to evaluate the expression against the visible rows — the user sees the output values inline before saving, catching typos and type mismatches early. Re-running an existing query for preview is cheap because the engine output is already in-memory on the SPA side; the expression evaluator can run in JS too (EvalEx isn't available client-side — see the open question below).
   - **First-iteration storage**: persist the user's column definitions in browser `localStorage`, scoped per user (NOT per cube — see definitions-library below). No server round-trip; survives page reload; not shared across browsers. The submission path serialises the definition into the query payload (so the engine processes it like any other client-supplied calc column for this query) — *not* a permanent server-side registration.
   - **Definitions library UI**: a panel (modal or side-drawer) listing every definition the user has authored, regardless of where it was originally created. Each row shows the name, the expression, and a **compatibility badge** for the cube currently in view:
       - ✅ *Compatible* — every column name referenced in the expression exists on the current cube. The user can attach the definition to the current query with one click.
       - ⚠️ *Partially compatible* — some referenced columns exist, some do not. The badge surfaces the missing names so the user can either rename their column or pick a different cube.
       - ❌ *Incompatible* — none of the referenced columns exist on the current cube. The row is shown but greyed-out; attaching the definition would just produce a column of `null`s.
     Compatibility is computed client-side from the definition's *referenced columns* set (extracted from the expression — see below) intersected with the current cube's `getColumns()`. The list is also filterable by name and by compatibility, so on a big library a user can quickly find "all my definitions that work on this cube".
   - **Referenced-columns extraction**: each definition needs to know which columns its expression touches, otherwise compatibility cannot be computed. Two options: (a) parse the EvalEx expression server-side at save time and record the variable set as part of the definition; (b) re-parse on every list render (cheap — definitions are short strings). Option (a) front-loads the cost and means an outdated `referencedColumns` field could lie if the user edits the expression without re-validating; option (b) keeps definitions canonical (just `{name, expression}`) but pays the parse cost per render. Lean towards (b) for simplicity; revisit if profiling shows the parse is hot.
   - **Later iteration — backend store**: introduce a *user-store* of column definitions (distinct from `ColumnsManager`, which is admin-scoped and bound to every query on the cube). The user-store records belong to the authenticated user and apply only when explicitly opted-into per query. Pivotable surfaces them in the column picker alongside the cube's regular columns AND in the definitions-library panel above (now backed by the server instead of `localStorage`). Persistence shape: probably `pivotable-app/persistence` reused (same module as favourites / chat history); fan-out across user devices is a free side-effect.
   - **Open question — preview evaluator**: EvalEx is a server-side dependency. The SPA preview either (a) round-trips a tiny "evaluate this expression against these rows" request, (b) reimplements a minimal expression subset in JS (good for the boolean-compare scenario, painful for arithmetic), or (c) lazy-fires the actual query with the calculated column wired in and shows the resulting view. Option (c) is the cheapest to ship but adds an extra network round-trip per keystroke during authoring; debounce.
- [Pivotable] User-authored **calculated measures**, in-SPA. Sister feature to the calc-column one above, but measures have richer typology — `Aggregator`, `Combinator`, `Partitionor`, `Dispatchor`, `Shiftor`, `Filtrator` … each with its own configuration shape. A reasonable first iteration scopes this down to **`Combinator` only**: the user picks one or more existing measures as underlyings, supplies a combination expression (EvalEx again), and gets a derived measure surfaced alongside the cube's regular ones. Same authoring UX as for columns (preview pane against the current view), same first-iteration storage (`localStorage`, per `(endpointId, cubeId, userId)`), same later iteration (backend user-store). Other measure types (`Aggregator` / `Partitionor` / `Dispatchor` / `Shiftor`) come later — they need more elaborate forms (target column, groupBy column, decomposition rule, filter editor) and probably one wizard per type. Open question: should the user-store be one bag-of-definitions per cube (columns + measures mixed) or a separate definitions store per kind? Mixed is simpler to surface in the wizard; separate is cleaner if the persistence layer ever grows kind-specific validation.
- [Resiliency] Replace `AdhocColumnUnsafe.checkColumnSize` with a *spilling* fallback rather than an `IllegalStateException`. Today, when a per-column accumulator (`MultitypeArrayColumn` and friends) is asked to hold more than `getLimitColumnSize()` rows, the call site throws and the entire query fails — even though the user's query was structurally valid; the cube just produced more rows than the hard cap. A spilling strategy would let large queries succeed at the cost of disk I/O: when an in-memory column approaches the cap, page hot keys to a backing store (DuckDB temp table, MapDB on disk, RocksDB, or a flat file with a custom encoder) and continue accumulating against that. Sub-questions: pick the backing store (DuckDB temp is already in the dependency tree; MapDB adds a small dep but is more general); decide between *eager* (always spill above N rows) and *adaptive* (spill only after free heap drops below T%); design the read path so downstream consumers (combinators, joins) don't need to know whether a column is in-memory or spilled. The current cap is a guardrail against runaway queries (`-Dadhoc.limitColumnSize=X` lets ops tune it), but it's a poor user experience — "your query failed because the engine is small" is unhelpful when the user has no way to know what to shrink. The fallback path should still be bounded by a configurable disk budget so the same protection applies, just at a different scale.

- [Performance] Table queries should be automatically partitioned table-side on some access. Typically, if one know the underlying data is partitioned by `c`, we should be able to query from `WHERE c % 8 = 0` to `WHERE c % 8 = 7` (WIP in `ModuloQueryPartitionor`).
- [Performance] Investigate [scala-polars](https://github.com/chitralverma/scala-polars) (JVM bindings for the Polars DataFrame library) as a backend for `ITabularRecordStream` reduction. Polars operates natively on Arrow record batches, so the Arrow IPC stream from DuckDB could be piped directly into a Polars `DataFrame` for GROUP BY / aggregation, avoiding the row-by-row Java accumulation loop in `TabularRecordStreamReducer`.
- [MCP] Long-lived API-token / OAuth 2.1 auth flow for MCP clients. Today `/mcp/**` falls through to `PivotableJwtWebfluxSecurity` and requires a Pivotable JWT in the `Authorization: Bearer …` header — works, but the SPA-issued JWT is short-lived. AI agents connecting via `.mcp.json` need either (a) a long-lived agent-specific API token issued by Pivotable, (b) refresh-token plumbing on the agent side, or (c) the MCP-spec OAuth 2.1 dynamic-client-registration / PKCE flow (canonical answer in protocol version 2025-03-26+, blocked today on Spring AI shipping the discovery endpoint and on Claude Code's MCP client implementing the flow end-to-end). The interim SPA "Copy MCP token" affordance buys time but is not the long-term posture.
- [Performance] Automatic customMarker stripping along the DAG. Once a measure has consumed the part of the `customMarker` it needs (canonical example: an FX measure consumes a `referenceCcy` marker), downstream steps should see a *simplified* customMarker so they can be shared across queries that differ only in the no-longer-relevant portion. Today the marker is propagated verbatim, so two queries with `referenceCcy=EUR` and `referenceCcy=USD` produce disjoint cache keys for every downstream step even when the underlying computation is identical post-FX. Related primitives already exist (`ICustomMarkerCacheStrategy#restrictToCacheImpact(Object)` for cache-key reduction); the missing piece is a declarative way for a measure to say "I consumed this slice of the marker, downstream may forget it".
- [Feature] Enable `ICombination` to declare their required levels (e.g. `getRequiredGroupBys()`). The query engine could then automatically infer the necessary `GroupBy`/`Partitionor` clauses when building sub-queries, removing the need for callers to specify them manually in most cases.
- [EXPLAIN] Introduce `EXPLAIN` vs `EXPLAIN ANALYZE` modes (inspired by SQL): `EXPLAIN` describes the query plan (measures DAG, querySteps, filters) without executing the query, enabling cheap plan inspection and validation; `EXPLAIN ANALYZE` executes the query and augments the plan with actual row counts, durations, and memory usage per step.
- [Performance] Merge the `CubeQueryStep` DAG and the `TableQueryStep` DAG into a single unified execution graph. Today the two DAGs are built and optimised independently; a combined optimiser could discover shared sub-computations across both layers, enabling further reduction of DB round-trips and elimination of redundant Adhoc-side re-aggregations. See `docs/cube-query-engine.md` for context.
- [Performance] `ChunkedList` (and `LongChunkedList`, `DoubleChunkedList`) could accept a `maximumChunkSize` cap, capping exponential growth at `AdhocColumnUnsafe.getDefaultColumnCapacity()`. Without a cap, the last tail chunk may be pre-allocated at a size far larger than the actual data, wasting memory when the final chunk is only partially filled.
- [Correctness] `ACubeQueryStep.equals()` (and `hashCode`) should distinguish steps whose `groupBy` columns are in different orders. Currently two steps with `{a, b}` and `{b, a}` may hash/equal identically even though they imply different sort orders, causing `isBreakSorting()` to produce wrong results and potentially triggering incorrect inducing rules. Fixing this may require revisiting deduplication logic and sorting assumptions in `JavaStreamInducedEvaluator` and `PartitionorQueryStep`.
- [Feature] BI tool integration (Tableau, PowerBI). Short-term: finish the WIP Calcite + Avatica JDBC connector (Tableau/PowerBI both speak JDBC out of the box). Mid-term: expose the same Calcite plan over [Arrow Flight SQL](https://arrow.apache.org/docs/format/FlightSql.html) (columnar gRPC wire protocol) consumed via [ADBC](https://arrow.apache.org/adbc/) (JDBC-shaped client API; Flight SQL is one of its drivers).
- [Quality] Wire an API-compatibility checker (e.g. [japicmp-maven-plugin](https://github.com/siom79/japicmp) or [Revapi](https://revapi.org/)) to compare each release artifact against the previously published version and flag binary / source-incompatible breaks. Useful once the public surface of `adhoc-model`, `adhoc-cell`, `adhoc-measures`, `adhoc-engine` etc. is stable enough that breaking changes warrant a deliberate decision rather than being silently introduced. Not relevant yet: Adhoc is still pre-1.0 and the public API is intentionally fluid; turning this on now would generate signal-less noise on every release. Re-evaluate around the move to a `1.x` line.
